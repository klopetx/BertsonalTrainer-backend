# Medallion Model: Bronze, Silver, and Validation

This document details how MinIO stores Bronze and Silver data, how session and word records are structured, and how normalization, validation, and duplicate handling work. It also covers the optional quarantine area and checkpoint namespace conventions.

## Bronze (raw layer)

- Storage: MinIO, format: Parquet, behavior: append-only and immutable.
- Captures every physical Kafka delivery, including technical retries and malformed payloads.
- Required metadata per row:
  - `kafka_topic`, `kafka_partition`, `kafka_offset`, `kafka_timestamp`
  - `ingested_at` (system timestamp)
  - `raw_payload` (untouched Kafka payload, typically as binary/string)
- Recommended representation: one row per Kafka record that stores metadata plus the raw payload blob.
- Partitioning: `bronze/session-events/ingestion_date=YYYY-MM-DD/part-*.parquet` (ingestion date is system-generated, not `business_date`).
- Bronze is the long-term audit source and enables future `rebuild_silver_from_bronze` tooling. Never mutate or delete Bronze data outside of disaster recovery processes explicitly approved later.

## Silver overview

- Generated by Spark Structured Streaming.
- Represents structured, normalized, classified data. Invalid words remain but are labeled.
- Two datasets:
  - `silver/sessions/`
  - `silver/session-words/`
- Recommended partitioning for both: `.../business_date=YYYY-MM-DD/part-*.parquet`.
- Silver may still contain technical duplicates because it reflects processable Kafka deliveries rather than definitive business deduplication.

## `silver/sessions` schema

| Field | Type | Purpose |
| --- | --- | --- |
| `source_record_id` | string | `topic:partition:offset` lineage for this physical delivery |
| `schema_version` | string | Input contract version |
| `event_id` | string | Logical event identifier (used during batch deduplication) |
| `payload_hash` | string | SHA-256 hash of the original Kafka payload |
| `session_id` | string | Functional session identifier |
| `user_id` | string | Simulated user identifier |
| `business_date` | date | Logical exercise day + partition key |
| `rhyme_id` | string | Daily rhyme identifier |
| `rhyme` | string | Rhyme text/suffix |
| `started_at` | timestamp | Session start (UTC) |
| `completed_at` | timestamp | Session completion (UTC) |
| `submitted_word_count` | integer | Count of submitted words, including duplicates/invalids |
| `valid_word_count` | integer | Count of distinct accepted words |
| `invalid_word_count` | integer | Count of rejected submitted words |
| `kafka_topic` | string | Kafka lineage |
| `kafka_partition` | integer | Kafka lineage |
| `kafka_offset` | long | Kafka lineage |
| `kafka_timestamp` | timestamp | Kafka record timestamp |
| `processed_at` | timestamp | When Spark produced the Silver row |

Rules:

- Empty sessions are preserved with zero counts.
- Technical retries may create multiple `silver/sessions` rows with the same `event_id` but different `source_record_id` values.
- `payload_hash` differentiates legitimate retries from integrity conflicts.
- Do not copy the `submitted_words` array into this dataset; use `silver/session-words` for word-level details.

## `silver/session-words` schema

| Field | Type | Purpose |
| --- | --- | --- |
| `source_record_id` | string | Links the word back to the exact `silver/sessions` row |
| `event_id` | string | Logical event identifier |
| `session_id` | string | Functional session identifier |
| `user_id` | string | Denormalized to simplify aggregations |
| `business_date` | date | Logical day + partition key |
| `rhyme_id` | string | Daily rhyme identifier |
| `word_index` | integer | Zero-based index inside `submitted_words` |
| `original_word` | string | Word exactly as submitted |
| `normalized_word` | string/null | After trim + lowercase + Unicode normalization; `null` if unusable |
| `is_valid` | boolean | Whether the word contributes to scores |
| `validation_reason` | string/null | Reason for rejection; `null` for accepted words |

Rules:

- Preserve original ordering using `word_index` so duplicates remain traceable.
- Only the first occurrence of a normalized valid word per session can be valid; later occurrences are marked `duplicate_in_session`.
- `normalized_word` retains accents/diacritics; do not strip language-specific characters.
- Derived metrics such as originality, rhyme difficulty, or final score do not belong in Silver.

## Normalization and validation flow

```
original word
  -> trim surrounding whitespace
  -> lowercase
  -> Unicode normalization
  -> duplicate check within session
  -> dictionary membership check
  -> rhyme suffix check (normalized word ends with normalized rhyme)
```

Suggested rejection reasons:

- `duplicate_in_session`
- `not_in_dictionary`
- `rhyme_mismatch`
- `empty_or_invalid_token`

The same normalization/validation logic must be reused by both streaming and batch components to ensure provisional and final scoring remain consistent.

## Relationship to PostgreSQL and Gold

- Silver is not the final idempotency boundary. Technical duplicates may exist until the batch deduplicates by `event_id` and applies the **first accepted event wins** policy per `user_id + business_date`.
- `serving.provisional_scores` uses Silver outputs to insert distinct events with database-side uniqueness and `ON CONFLICT DO NOTHING` semantics.
- Gold tables rely on Silver for their structured inputs and apply transactional replace-by-scope writes during batch execution. See `docs/postgres-model.md`.

## Quarantine (P2)

- A dedicated MinIO area will capture unprocessable events with categories such as `JSON_PARSE_ERROR`, `UNSUPPORTED_SCHEMA_VERSION`, `CONTRACT_VALIDATION_ERROR`, `BUSINESS_RULE_VIOLATION`, `INTEGRITY_CONFLICT`, and `LATE_EVENT`.
- Word-level invalidity does **not** trigger quarantine; invalid words remain in `silver/session-words` with the correct `validation_reason`.

## Checkpoint namespace

- Streaming checkpoints reside under `system/checkpoints/streaming/<query-name>/` within MinIO.
- Each Structured Streaming query must use a dedicated checkpoint path so restarts resume exactly-once semantics relative to Kafka offsets.
- No watermarking is required; business late-event handling is enforced via the cutoff documented in `docs/batch-and-scoring.md`.
